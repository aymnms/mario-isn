# Plan — mario-isn

> Ce fichier est la seule source de vérité de l'avancement. Il doit refléter la réalité à tout moment. Commit à chaque mise à jour.

## Raisonnement du découpage

Les jalons suivent directement les 4 issues GitHub ouvertes, dans l'ordre de dépendance et d'effort identifié en `AUDIT.md` §7. J1 (fix release) est traité en premier car il bloque toute distribution du projet et est de faible effort/risque isolé (un seul paramètre CI, cf. AUDIT.md §4-5). J2 (bundling des libs) est ensuite nécessaire pour qu'une release distribuée soit réellement utilisable (AUDIT.md §4, #15). J3 (Windows) est traité en dernier car c'est le chantier le plus large (nouveau job CI jamais validé, cf. AUDIT.md §3) et le moins bloquant dans l'immédiat (aucune régression actuelle, juste une plateforme absente).

## Jalons

- **J1** — Fix pipeline de release — corriger le téléchargement d'artefact dans `release.yml` pour que `semantic-release` publie enfin une release (#16).
- **J2** — Bundler les libs SDL2 — embarquer SDL2/SDL2_image/SDL2_mixer dans les artefacts macOS et Linux pour une exécution sans dépendances système (#15).
- **J3** — Build et CI Windows — réactiver le job Windows de `build.yml` (vcpkg + build + packaging) (#8, #9).
- **J4** — Build macOS Intel via Rosetta — demande explicite de l'utilisateur (hors des 4 issues initiales), sur le modèle d'une recette déjà validée sur un autre de ses projets (PyInstaller/Python) : cross-compilation `clang -arch x86_64` depuis le runner Apple Silicon `macos-latest` (pas de runner Intel natif fiable disponible), avec un second Homebrew x86_64 sous Rosetta pour les libs SDL2.
- **J5** — Fiabilisation et dette technique post-v1.2.0 — les 4 issues initiales sont livrées (release v1.2.0) ; ce jalon reprend les points laissés en dette dans `AUDIT.md` §6-7 et la Roadmap du README, phasés par risque/effort :
  - **Phase 1 (fiabiliser ce qui est livré)** : smoke test CI isolé validant le bundling Linux en conditions réelles (`J2-3`), cache vcpkg pour ne pas recompiler SDL2 à chaque run Windows (`J3-6`).
  - **Phase 2 (hygiène rapide, effort faible)** : supprimer la console Windows superflue (`J3-5`), `clang-format`/`.editorconfig` (AUDIT §7 reco #4).
  - **Phase 3 (dette technique de fond, effort élevé)** : extraire un noyau de logique de jeu découplé de SDL, prérequis bloquant pour tout test unitaire (AUDIT §7 reco #5).
- **J6** — Hotfix : régression macOS "app endommagée" — signalée par l'utilisateur (`.app` refuse de s'ouvrir sur Intel et Apple Silicon depuis la 1.2.0, erreurs Gatekeeper "endommagé"/-47). Diagnostiquée et corrigée en dehors de tout jalon planifié, priorité immédiate vu l'impact (releases publiées cassées pour tous les utilisateurs macOS).
- **J7** — Hotfix : mêmes symptômes ("build CI verte, cassé pour un utilisateur réel") sur Windows et Linux, signalés par l'utilisateur juste après validation de `J6`. Windows : `VCRUNTIME140.dll` (et les DLL Universal CRT associées) jamais embarquées, ni pour `mario_isn.exe` ni pour `SDL2.dll` (précompilée par vcpkg, même dépendance). Linux : build CI sur `ubuntu-latest` (24.04, glibc 2.39), donc les `.so` embarqués exigent une glibc plus récente que celle de l'utilisateur — la glibc n'est délibérément jamais embarquée (compatible uniquement vers l'avant), donc le binaire refuse de charger sur un système plus ancien.
- **J8** — Après confirmation que Windows/Linux fonctionnent (`J7`), l'utilisateur remonte deux points d'expérience distincts : (1) les releases embarquent des fichiers qui n'ont rien à voir avec le jeu ; (2) Windows SmartScreen affiche un avertissement "éditeur inconnu" faute de signature de code, ce qui dégrade l'expérience de lancement.
- **J9** — Clarification de l'utilisateur sur `J8` point (1) : la vraie demande n'était pas "ne pas embarquer de fichiers hors-jeu" (déjà traité), mais "une seule chose à lancer, pas un dossier avec plein de fichiers visibles à gérer" — comme le `.app` macOS. Décidé avec l'utilisateur (question posée) : installateur NSIS pour Windows (raccourci Menu Démarrer, désinstalleur), AppImage pour Linux (fichier unique auto-suffisant, pas d'installation).
- **J10** — Hotfix : fuite mémoire signalée par l'utilisateur après test réel des installateurs Windows/AppImage Linux publiés en `J9` — le jeu ralentit après quelques minutes (quelques secondes sur sa machine Linux, peu de RAM). Diagnostiquée par audit de tout le code de rendu : `SDL_DestroyTexture` n'est appelé nulle part dans tout le dépôt, et plusieurs fonctions du chemin de rendu très chaud (jusqu'à 60 fois/seconde) rechargent une texture PNG depuis le disque à chaque appel au lieu de la mettre en cache — une texture GPU jamais libérée à chaque frame.

Vérifié en local avec un test de contrôle : la version sans `libSDL3.dylib` embarquée crashe bien en `SIGABRT` (134, reproduit le bug signalé), la version corrigée reste up.
